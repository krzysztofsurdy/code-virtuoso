## Major changes

| Change | Effect on a server |
|---|---|
| No protocol-level sessions, no `Mcp-Session-Id` header | No per-connection context. List endpoints do not vary per connection |
| No `initialize` or `notifications/initialized` handshake | Each request carries `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in `_meta`. Clients should send `clientInfo`. Servers should return `serverInfo` in result `_meta`. A version mismatch returns `UnsupportedProtocolVersionError` |
| `server/discover` required | Servers must implement it to advertise versions, capabilities, and identity. Clients may call it first, or use it as a compatibility probe on stdio |
| `subscriptions/listen` replaces the HTTP GET endpoint and `resources/subscribe` | One long-lived POST response stream for opted-in notifications (`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions`). Request-scoped notifications such as progress stay on the request's own stream |
| `ping`, `logging/setLevel`, and `notifications/roots/list_changed` removed | Log level is set per request through `io.modelcontextprotocol/logLevel` in `_meta`. Do not emit `notifications/message` for requests that did not include it |
| Tasks moved to an extension (`io.modelcontextprotocol/tasks`) | Poll with `tasks/get`, send input with `tasks/update`. `tasks/result` blocking and `tasks/list` are gone. Servers may return task handles unsolicited |
| Multi Round-Trip Requests (MRTR) | Replaces server-initiated `roots/list`, `sampling/createMessage`, and `elicitation/create`. See below |
| Every result has `resultType` | `complete` or `input_required`. Clients treat a missing field from an older server as `complete` |
| SSE resumability removed (`Last-Event-ID`, event IDs) | A broken stream loses the request. Clients must re-issue it as a new request with a new ID. Write operations need idempotency |

## Minor changes

- `extensions` field added to client and server capabilities.
- OpenTelemetry trace context (`traceparent`, `tracestate`, `baggage`) documented for `_meta` (SEP-414).
- `tools/list` should be in a deterministic order, which helps client caching and LLM prompt cache hits.
- Streamable HTTP POST requests require `Mcp-Method` and `Mcp-Name` headers. Tool parameters can be mirrored to headers with `x-mcp-header` (SEP-2243).
- `ttlMs` and `cacheScope` (`public` or `private`) are required on `tools/list`, `prompts/list`, `resources/list`, `resources/read`, and `resources/templates/list` results (SEP-2549).
- Resource-not-found error code changed from -32002 to -32602.
- Authorization servers should include `iss` (RFC 9207), and clients must validate a present `iss` before redeeming the code (SEP-2468).
- Clients must give an appropriate `application_type` during Dynamic Client Registration (SEP-837).
- Client credentials are bound to the issuing authorization server and must be keyed by issuer (SEP-2352).
- `inputSchema` and `outputSchema` accept any JSON Schema 2020-12 keywords, and `structuredContent` can be any JSON value (SEP-2106).
- `notifications/elicitation/complete` and `elicitationId` removed.
- Error codes -32020 to -32099 are reserved for the spec (`HeaderMismatch` is -32020, `MissingRequiredClientCapability` -32021, `UnsupportedProtocolVersion` -32022). -32000 to -32019 stay implementation-defined.

## Deprecated

Deprecated features remain in the spec and keep working during a window of at least twelve months, under the [feature lifecycle policy](https://modelcontextprotocol.io/community/feature-lifecycle). New implementations should not adopt them.

| Deprecated | Use instead |
|---|---|
| Roots | Tool parameters, resource URIs, or server configuration for paths |
| Sampling | Call your LLM provider directly |
| Logging | stderr on stdio, or OpenTelemetry |
| HTTP+SSE transport | Streamable HTTP |
| `includeContext` values `thisServer` and `allServers` | Omit the field or use `none` |
| OAuth Dynamic Client Registration (RFC 7591) | Client ID Metadata Documents. DCR stays for authorization servers that lack support for them |

## Building a stateless server

The spec's own statement: a server processes each request independently, and no state should be inferred from earlier requests, even on the same connection.

- Create the server and transport per request, or make them hold no per-client data. The TypeScript v2 docs show this with `sessionIdGenerator: undefined`.
- Read protocol version and client capabilities from each request's `_meta`. Never cache them against a connection.
- Any state that spans calls goes behind an explicit handle that the model passes as a tool argument. Store it in a shared store (database, cache), not in process memory, so any instance can serve the next call.
- Do not require clients to reuse a connection or process. On stdio, clients should not tie the process lifetime to one conversation.
- `tools/list` may vary by the credentials on the request (for example, only tools the granted scopes permit), but not by connection or by side effects of earlier calls.
- Handle retries. With no stream resumption, a dropped response means the client sends the call again with a new ID. Use idempotency keys for writes.
- Set `ttlMs` and `cacheScope` on list results. Use `private` for lists that vary by user.
- Log from stderr on stdio and use OpenTelemetry for traces. Do not write anything to stdout that is not a valid MCP message.

Handle security: possession of a handle must never count as authentication. Use random handles, bind them to the verified user server-side, and expire them.

## Multi Round-Trip Requests

When a tool needs input mid-call (a confirmation, a missing field, a choice), the server no longer sends a request back on an open stream. It ends the request with an `input_required` result, and the client retries the original call with the answers.

1. Client sends `tools/call` (also supported: `prompts/get`, `resources/read`).
2. Server returns `resultType: "input_required"` with `inputRequests` (a map of server-chosen keys to `elicitation/create`, `sampling/createMessage`, or `roots/list` requests) and optionally an opaque `requestState`.
3. Client gathers the input and sends the same call again with a new JSON-RPC ID, plus `inputResponses` keyed to match, and the exact `requestState` echoed back.
4. Server completes, or asks again if inputs are missing.

Server rules that matter:

| Rule | Why |
|---|---|
| Include at least one of `inputRequests` or `requestState` | An empty `input_required` is invalid |
| Do not request an input type the client has not declared support for | The client cannot answer it |
| Treat `requestState` as attacker-controlled | It round-trips through the client. If it affects authorization, resource access, or business logic, protect it with an HMAC or AEAD and reject anything that fails verification |
| Bind `requestState` to the principal, a short expiry, and the originating request (method plus a digest of key parameters) | Stops replay across users and requests |
| Enforce single use on the server when it matters | Integrity protection does not stop replay inside the expiry window |
| Do not assume the client will retry | The user may walk away |

The design benefit: no shared storage layer or sticky load balancing is needed, because the retry carries all the context. Note that Sampling and Roots are deprecated even though MRTR can still carry them, so use MRTR for elicitation (asking the user) and avoid building on the other two.

## Streamable HTTP details

- `POST /mcp` with `Content-Type: application/json`, an `MCP-Protocol-Version` header that matches `_meta`, `Mcp-Method`, and `Mcp-Name` for `tools/call`, `resources/read`, and `prompts/get`. The server may answer with one JSON object or an SSE stream.
- A header that is missing, mismatched with the body, or has invalid characters is a validation failure (400, `HeaderMismatch`). An unsupported version is a 400 with `UnsupportedProtocolVersionError`. An unknown method is a 404 with -32601.
- Validate the `Origin` header on all connections to stop DNS rebinding, and answer an invalid one with 403. Bind local servers to 127.0.0.1, not 0.0.0.0, and require authentication.
- Do not mark sensitive parameters (passwords, keys, PII) with `x-mcp-header`, since network intermediaries see headers.

## Migration order from 2025-11-25

1. Pin and read the SDK release notes. Pick an SDK release that implements 2026-07-28 (the TypeScript v2 line does, per its README). Confirm for the Python SDK you use.
2. Remove session assumptions: drop `Mcp-Session-Id` handling and any per-connection storage. Move shared state into handles backed by a shared store.
3. Implement `server/discover` and emit `resultType` on every result.
4. Replace server-initiated requests with MRTR. Delete code that depends on `elicitation/complete` and `elicitationId`.
5. Remove use of Roots, Sampling, and Logging. Pass paths as tool parameters, call the model provider directly, and log to stderr or OpenTelemetry.
6. Sort `tools/list` and set `ttlMs` and `cacheScope`.
7. Update auth: support Client ID Metadata Documents, validate `iss`, keep the `resource` and audience checks. Treat DCR as legacy support only.
8. Replace HTTP+SSE endpoints with Streamable HTTP, and add the `Mcp-Method` and `Mcp-Name` headers.
9. Make writes idempotent, since stream resumption is gone.
10. Run your eval set and your auth unit tests again.

Both the legacy and the new era can share a codebase: the TypeScript v2 `createMcpHandler` serves 2025-era traffic statelessly and passes the client's era to your factory.
